■ 用語メモ (先に読むと後が楽です)
・クラス      : 「設計図」。 データ(変数)と動き(関数)をひとまとめにしたもの。
                例) Fighter1 は「格闘キャラ」の設計図。
・オブジェクト: 設計図から作った実物。
・親クラス(基底クラス) : 共通部分をまとめた元のクラス。 (FighterBase, Scene)
・継承        : 親の機能を受け継いで子クラスを作ること。
                class Fighter1 : public FighterBase  と書く。
・仮想関数(virtual) : 子クラスが「上書きしてよい」関数。
・純粋仮想関数(= 0) : 親では中身を書かず、子が必ず作らないといけない関数。
                1つでも持つクラスは「抽象クラス」で、そのままでは作れない。
・override    : 「親の関数を上書きしているよ」という印。 書き間違いを教えてくれる。
・フレーム    : 画面を1回書き換える単位。 このゲームは1秒に60回(60fps)。
                1フレームは約0.0167秒。
・発生 / 持続 / 硬直 : 攻撃の3つの時間。
                発生 = ボタンを押してから判定が出るまで
                持続 = 判定が出ている間
                硬直 = 判定が消えてから動けるようになるまで
・当たり判定  : 当たったかを調べるための見えない四角形。
                攻撃の四角と、体の四角が重なれば「当たり」。
・シーン      : ゲームの「画面の種類」。 タイトル、ゲーム中、ポーズなど。
・スマートポインタ(unique_ptr / shared_ptr) :
                作ったものを自動で片付けてくれる入れ物。
                unique_ptr = 持ち主が1人だけ
                shared_ptr = 複数で共有(最後の持ち主がいなくなると消える)
・名前空間(namespace) : 名前の置き場所。 Game::kScreenWidth のように「場所::名前」で使う。
・マジックナンバー : コードに直接書かれた、意味のわかりにくい数字(例: 450, 1230)。
                変更するときに直し忘れやすい。
・ヒットストップ : 当たった瞬間に一瞬だけ動きを止めて、手応えを出す演出。
・のけぞり(やられ硬直) : 攻撃を受けた側が、しばらく動けなくなる状態。
・先行入力    : 動けない間に押したボタンを少し覚えておき、動けるようになった
                瞬間に出す仕組み。
・ビルド生成物 : ビルド(実行ファイルを作る作業)で自動的にできるファイル。
                x64 フォルダの中身など。 人によって変わるので Git には入れないのが普通。

■ 1. 現在実装されている機能
--------------------------------------------------------------
【事実】 ここに書いたものは、すべてコードを読んで確認した。

(A) ゲームの土台   (main.cpp, Game.h)
・ウィンドウ 1280×720 で起動。 タイトルは「BONK!」。
・1秒に約60回の更新(60fps)。 ESC キーで終了。
・1フレームの流れ: 入力を更新 → いまのシーンを更新 → 全シーンを描く → 画面を入れ替え。

(B) 3つの画面(シーン)
・タイトル : 「BONK!」と点滅する「PRESS ENTER」、操作説明。 Enter でゲーム開始。
・ゲーム   : 下の (C)。
・ポーズ   : ゲーム中に P キーで、ゲーム画面の上に重なる(後ろに暗いゲーム画面が見える)。
              上下キー + Enter で CONTINUE(つづける) / BACK TO TITLE(タイトルへ)。
              P をもう一度押しても戻れる。

(C) ゲーム画面   (GameScene, Fighter1, Stage)
・2人同時プレイ。 1P = 赤(左側・右向き)、 2P = 青(右側・左向き)。 見た目は四角形。
      1P : A / D 移動、 W ジャンプ、 J 攻撃
      2P : ← / → 移動、 ↑ ジャンプ、 , (カンマ) 攻撃
・移動 : 前進 5px/フレーム、 後退 3px/フレーム。 向いている方向が「前」。
・向き : 地上で、攻撃していないときは、自動で相手のほうを向く。
・ジャンプ : 垂直・前・後ろの3種類。
              跳んだ瞬間に押している方向キーで決まり、空中では変えられない。
              初速 -12、 重力 0.5/フレーム。
              【計算】 高さ 約140px、 空中にいる時間 約47フレーム(約0.8秒)。
・画面の左右の外には出ない。
・床 : 高さ 500 の白い線。 足元が床に着くと着地。
・弱攻撃 1種類(地上のみ):
      押した瞬間にだけ出る(押しっぱなしでは連続しない)。
      発生 5フレーム / 持続 3フレーム(5〜7フレーム目) / 全体 20フレーム(残りが硬直)
      ダメージ 5。 判定の大きさ 幅40 × 高さ30。 体の前、体の上から20px下。
      攻撃中は移動もジャンプもできない。
      1回の攻撃で当たるのは1回だけ。
      判定が出ている間は黄色い枠で見える(確認用の表示)。
・ダメージ : HP は 100。 当たると 5 減る。 0 で止まる(マイナスにならない)。
・HPバー   : 画面上部の緑のバー(確認用の仮表示)。 1P は左上、 2P は右上。

(D) 入力の仕組み   (Input)
・キーを「名前」で調べる Input クラスがある。 登録済みの名前は4つだけ:
      ok (Enter) / pause (P) / up (↑, W) / down (↓, S)
・IsPressed(押している間) と IsTriggered(押した瞬間) を使い分けられる。
・ただし、戦闘中のキー(移動・ジャンプ・攻撃)は Input を通さず、
  DxLib の CheckHitKey を直接呼んでいる。

(E) コードはあるが「まだ使われていない」もの
・Mouse (マウス入力) : 毎フレーム Update は呼ばれるが、使っている場所がない。
・Vec2.h (2次元ベクトル) : どこからも使われていない。
・m_isGuarding (ガード中フラグ) : 宣言と初期化だけで、使われていない。
・Stage::Update / Stage::End : 中身が空で、呼ばれてもいない。
・GameScene の m_frameCount : 数えているだけで、使われていない。

(F) コスト表との対応 【推測】
  コスト表(BONK!)の項目名と、いまのコードを「私の解釈で」対応づけると、
  できているのは次のあたり。
      歩き / ジャンプ / 当たり判定(長方形) / HP / タイトル・ポーズなどの画面
      弱攻撃の1発目
  ※ 項目の対応づけは解釈なので、ずれているかもしれない。

■ 3. クラス同士の関係
--------------------------------------------------------------
【事実】 (include と、変数の持ち方から確認)

(A) 継承(親子)    「子 → 親」
      TitleScene  → Scene
      GameScene   → Scene
      PauseScene  → Scene
      Fighter1    → FighterBase
    ※ Scene と FighterBase は抽象クラス。 そのままでは作れず、必ず子を作る。

(B) 「持っている」関係
      main()            Input と SceneController を1つずつ持つ
      SceneController   Scene を list(並び)で持つ。 一番後ろ = 一番上に見えている画面
      Scene             SceneController への参照を持つ
                        → 子のシーンが自分で「切り替えて」と頼める
      GameScene         FighterBase を2つ(unique_ptr)、 Stage を1つ持つ
                        中身は2つとも Fighter1

(C) 画面が切り替わる流れ(誰が誰を呼ぶか)
      起動 → TitleScene
      TitleScene  --Enter-->        ChangeScene(GameScene)     [入れ替え]
      GameScene   --P-->            PushScene(PauseScene)      [重ねる]
      PauseScene  --P / CONTINUE--> PopScene                   [外してゲームに戻る]
      PauseScene  --BACK TO TITLE-> ResetScene(TitleScene)     [全部捨ててタイトルへ]

(D) 1フレームの流れ
      main の while ループ
        1. input.Update()              キー入力を更新
        2. Mouse::Update()             (使われていない)
        3. controller.Update(input)    一番上のシーンだけ更新
             GameScene の場合:
               Pでポーズ判定 → 2人の向き調整(FaceTo) → 2人の Update
               → 当たり判定(CheckAttackHit) を2回(1P→2P、 2P→1P)
        4. controller.Draw()           全部のシーンを下から順に描く
        5. ScreenFlip → 約1/60秒待つ

(E) つながっていない部分
      ・Fighter は Input を使わない(キーを自分で CheckHitKey で調べる)。
      ・Stage の床の高さ(500)は Fighter に渡されていない。
        Fighter1.cpp に同じ 500 が別に書いてある。
      ・当たり判定は、FighterBase の関数 + GameScene.cpp の CheckAttackHit で行う。
        CheckAttackHit はクラスではなく、そのファイル内だけで使う関数。

(F) 気をつける約束(いまのコードは守れている)
      ChangeScene / PopScene / ResetScene を呼ぶと、呼んだ自分(そのシーン)が
      消えることがある。 呼んだら、すぐ return して、自分の変数を触らない。
      (TitleScene.cpp, PauseScene.cpp でこの形になっている)

■ 5. 今後のおすすめ実装順序   【提案】
--------------------------------------------------------------
考え方:
  ① 小さな直しを先に済ませる → ② 「当たった」を手応えのあるものにする
  → ③ 試合として終わらせる → ④ 技を増やす → ⑤ 企画書の目玉(浮かして追撃)
  → ⑥ 見た目・音・CPU の順。
  前の段階が土台になるので、上から順に進めると、やり直しが少ない。

0. 準備(どれも小さい作業)
     ・ジャンプが押しっぱなしで連続する点を直す         (6-a)
     ・.gitignore に x64 などを足して、生成物を Git から外す (6-b)
     ・床の高さを1か所にまとめる                         (6-c)
   理由: 小さい作業で、あとで起きる混乱や衝突を減らせる。

1. のけぞり(やられ硬直) + ノックバック(少し後ろへ押される)
   理由: 今は当てても相手が無反応。 ガード・コンボ・打ち上げが、
         どれも「やられ状態」を使うので、いちばんの土台になる。
   やること: FighterBase に m_hitStun(のけぞりの残りフレーム)を追加。
         TakeDamage で数字を入れ、Update の最初で
         「のけぞり中は何もせず return」する。

2. 勝敗判定とリザルト画面
   理由: HP が0でも試合が終わらない。 ResultScene を作って ChangeScene するだけなので、
         シーン管理の練習にもなる。

3. ガード
   理由: m_isGuarding が用意済み。 後ろ入れでガードし、GameScene 側で
         ダメージを0にする。 1(のけぞり)の後なら、ガード硬直も同じ仕組みで作れる。

4. 攻撃データの整理 + 入力の整理
     ・攻撃の数字(発生・持続・ダメージ…)を構造体(変数のまとまり) AttackData に
       まとめる。
     ・SetKeys を、キーの種類が増えても困らない形(構造体など)にする。
   理由: 強攻撃や空中攻撃を足すと変数がどんどん増え、いまの作りでは管理しにくい。
         (6-d, 6-f)

5. 強攻撃(K)・弱攻撃の3連・先行入力・ヒットストップ
   理由: 4 の AttackData ができていれば、攻撃を「データを1つ足す」感覚で増やせる。
         先行入力とヒットストップは、攻撃が増えてからのほうが効果を確かめやすい。

6. 打ち上げ・空中攻撃・空中コンボ(企画書の中心)
   理由: 1(やられ状態)と 5(強攻撃)が前提。 いちばん難しいので、土台が固まってから。

7. 回避・ステップ・しゃがみ・投げ(コスト表にある項目)

8. 戦闘の入力を Input クラスに移す(1P用・2P用の名前を分ける)
   ※ 4 と一緒に前倒ししてもよい。 コントローラー対応やキーコンフィグの前には済ませたい。

9. 画像・アニメーション、サウンド(BGM・効果音)、UI(タイマー・コンボ表示)
   理由: ルールと技が固まってから作ると、作り直しが少ない。

10. CPU(1人プレイ)、2人目のキャラ(Fighter2)、キャラ選択
   理由: 技のしくみが完成してから。 CPU は「プレイヤーと同じ操作」で動かせる作りだと楽。

■ 6. 現在のコードで気になる点
--------------------------------------------------------------
重要度: [高] 早めに直したい / [中] 機能を増やす前に直したい / [低] 気づいておく程度
(動かして確かめていないものは、【推測】と書いてある)

[高] 6-a ジャンプが、押しっぱなしで連続する
    場所: Fighter1.cpp 99行目
        if (CheckHitKey(m_keyUp) && m_air == false && m_isAttacking == false)
    【事実】 条件が「いま押している」だけで、「前のフレームは押していなかった」を
            見ていない。 コメントには「押した瞬間」と書いてあるが、コードは違う。
            (攻撃は m_prevAttackKey で「押した瞬間」を見ている。ジャンプだけ書き方が違う)
    【推測】 ↑キー(W)を押したままだと、着地した次のフレームでまた跳ぶはず。
    【提案】 攻撃と同じく、m_prevUpKey を作って「押した瞬間だけ」にする。

[高] 6-b ビルド生成物が Git に入っていて、.gitignore が Unity 用のまま
    【事実】 x64 フォルダの中身などが Git で管理されている。
              BONK!/BONK!/x64 ... 75ファイル、 BONK!/x64 ... 1ファイル
              BONK!(/BONK!/x64 ... 24ファイル、 SideScrollShmup 側にも 67ファイル
    【事実】 .gitignore の1行目の説明が「Unity project」で、Unity 用のひな形のまま。
            x64 / Debug / *.exe / *.ilk / *.tlog は書かれていない(*.pdb はある)。
            BONK!/Log.txt も Git に入っている。
    【推測】 ビルドするたびにこれらが「変更あり」と表示され、マージ(ブランチの取り込み)で
            衝突しやすい。
    【提案】 .gitignore に x64/ と Log.txt などを足す。 すでに管理されているものは
            git rm --cached で管理から外す必要がある(ファイル自体は消えない)。

[高] 6-c 床の高さ(500)が、複数の場所に別々に書かれている
    【事実】 Fighter1.cpp の kGroundY = 500、 Stage.h の m_groundY = 500、
            Stage.cpp の m_groundY = 500。 Fighter は Stage の値を見ていない。
    【推測】 ステージの床を変えると、キャラが浮く/沈む。
    【提案】 Game.h に kGroundY を1つ置いて、全員がそれを使う。

[中] 6-d 攻撃の数字が二重に書かれている
    【事実】 発生5・終了8・全体20・ダメージ5・幅40・高さ30・位置20 が、
            FighterBase.cpp の初期値と Fighter1.cpp の Init の両方に同じ値で書いてある。
    【提案】 強攻撃などを足す前に、AttackData(構造体)にまとめて1か所にする。
            (おすすめ順序 4)

[中] 6-e 移動・ジャンプ・攻撃の処理が、全部 Fighter1 の中にある
    【事実】 Fighter1::Update (約110行)に、どのキャラでも共通の処理が入っている。
    【推測】 2人目のキャラ(Fighter2)を作るとき、コピーすると直す場所が2倍になる。
    【提案】 共通の処理は FighterBase に移し、キャラごとに違う部分(技の数字や
            特別な技)だけを子クラスに残す。

[中] 6-f 入力の方法が2つある
    【事実】 シーン(タイトル・ポーズ)は Input クラス、戦闘は CheckHitKey を直接呼ぶ。
            SetKeys は「右・左・上・攻撃」の4つしか渡せない(キーが増えると引数が増える)。
    【推測】 ガード・強攻撃・コントローラーを足すとき、直す場所が増える。
    【提案】 戦闘のキーも Input の「名前」で扱う(1P用・2P用の名前を分ける)。

[中] 6-g HPバーなどに、数字が直接書かれている(マジックナンバー)
    【事実】 GameScene.cpp 115〜121行: HP × 4、 450、 1230、 830 など。
    【推測】 HP が100以外のキャラ(体力が多いキャラ等)を作ると、バーがはみ出す/足りない。
    【提案】 HP の最大値を変数にして、「HP ÷ 最大HP × バーの長さ」で描く。

[中] 6-h 2人のキャラが重なれる
    【事実】 GameScene に、体どうしを押し離す処理がない。
    【推測】 相手の中を通り抜けられるはず。 動かして確かめたい。

[中] 6-i 古いコピーと、教材が同じリポジトリに入っている
    【事実】 「BONK!(」(カッコ付き)というフォルダがある。 中に Fighter2.cpp、
            SceneMain.cpp、README_作業内容.txt がある。 README に
            「シーン管理・2人プレイヤー仮実装版」と書かれている。
    【推測】 BONK! フォルダより古い版のコピーのように見える。
    【事実】 SideScrollShmup フォルダ(171ファイル、約51MB)と、
            SideScrollShmup (1).zip (約2.5MB)も入っている。
    【提案】 古いコピーと教材は、リポジトリの外で管理するか、消してよいか決める。
            (消す前に、バックアップを取ってから)

[低] 6-j 名前や初期値のちぐはぐ
    【事実】 FighterBase.cpp の m_Jump の初期値は -60 だが、Fighter1::Init で -12 に
            上書きされている(動作に害はないが、紛らわしい)。
    【事実】 HP の変数だけ名前が hp で、ほかの変数のように m_ が付いていない。

[低] 6-k 使われていないものの整理
    【事実】 Mouse、 Vec2.h、 m_isGuarding、 Stage::Update/End、 m_frameCount。
    【提案】 近いうちに使うもの(m_isGuarding など)は残し、使わないものは消すか、
            「将来用」とコメントを付ける。

[低] 6-l 文字コードが混ざっている
    【事実】 ソース23ファイルのうち、 UTF-8 の BOM(ファイルの先頭の目印)が
            付いているのが14、付いていないのが9(日本語を含むのは7)。
    【事実】 プロジェクト設定に、UTF-8 を指定するオプションは見当たらない。
    【推測】 ふだんは問題なく動くことが多いが、日本語のコメントが文字化けしたり
            警告が出たりしたら、この混在が原因かもしれない。 いまは対応不要。

[低] 6-m メインループの待ち方
    【事実】 main.cpp の while で、1/60秒たつまで何もせず回り続けている。
    【推測】 待っている間も CPU を使い続ける(DxLib のひな形由来)。
            いまは気にしなくてよい。

[低] 6-n 当たったあとも、黄色い判定の枠が消えない
    【事実】 Fighter1::Draw は m_attackHit を見ず、判定の時間中はずっと枠を描く。
            (ダメージは1回だけ入る)  見た目だけの違い。


[よくできている点]
・シーン管理(Scene / SceneController)が、ゲーム本体と分かれていて、
  タイトル・ポーズの追加が簡単。
・攻撃が「発生・持続・硬直」の変数で表されていて、攻撃を増やしやすい土台になっている。
・攻撃の「押した瞬間」判定、同じ攻撃で1回だけ当たる処理が正しく書けている。
・コメントが丁寧で、あとから読み返しやすい。

[動かして確かめるとよいこと]【推測】の確認用
・W(2Pは↑)を押しっぱなしにして、着地した瞬間にまた跳ぶか   (6-a)
・2人を近づけて、体が重なるか                                (6-h)
・日本語のコメントが、Visual Studio で文字化けしていないか    (6-l)
